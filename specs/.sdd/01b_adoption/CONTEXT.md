# Stage 01b: Adopt Existing Codebase into SDD

Reverse-engineer the spec set from a working codebase, then capture what the system *actually does* as a characterization oracle. From then on, any rewrite or refactor can be proven observationally equivalent to the original.

This stage is an **alternative to Stage 01 (Brainstorming)**. It produces the same artifacts as Stages 01–02, extracted from existing code and behavior instead of designed from scratch.

## When to Use This Stage (instead of Stage 01)

- The project has working code but no `specs/SPEC.md`
- The user wants to bring an existing codebase under SDD management, or to rewrite it equivalently
- The user says "adopt", "onboard", or "reverse-engineer the spec"

## Inputs

- Layer 4 (working): Existing codebase (source, config, package manifests), existing tests, docs, git history
- Layer 4 (working): A runnable instance of the existing system (needed for recording)
- Layer 3 (reference): `../_config/spec-template.md`, `../_config/decision-log-template.md`, `../_config/design-template.md` (UI only)
- Layer 3 (reference): `../_config/references/completeness-checklist.md`, `../_config/references/extraction-closure.md`
- Layer 3 (reference): `../_config/references/systems-standards.md`, `../_config/references/oracle-standard.md`

## Process

### Step 1: Configure Adoption Parameters

Present adoption parameters to user and get confirmation before scanning:

| Parameter | Default | Description |
|-----------|---------|-------------|
| Analysis Depth | `thorough` | `quick` / `standard` / `thorough` |
| Focus Modules | `all` | Directories/modules to prioritize |
| Include Git History | `yes` | Mine git log for decisions |
| Map Existing Tests | `yes` | Inventory tests & map to invariants |
| Project Type | auto-detect | One of `../_config/references/completeness-checklist.md` (confirm with user) |
| Run Command | auto-detect | How to start the existing system for recording |

**⛔ GATE:** ⊥ begin analysis until user confirms parameters.

### Step 2: Scan & Inventory

1. Read folder tree, package manifests, entry points, README
2. Identify key modules, responsibilities, public interfaces (routes, commands, exported API), dependencies
3. `Map Existing Tests = yes` → read test files, categorize (unit/integration/e2e), note coverage
4. `Include Git History = yes` → mine git log for architectural decisions & evolution

### Step 3: Characterization Closure

Apply the 4 Extraction Closure dimensions (`../_config/references/extraction-closure.md`) to the *existing* system, answering each item from code evidence (file:line). ∀ item code cannot answer → one targeted question to the user (one question per message). Subjective confidence scores are forbidden; the gate is the closure report.

**⛔ GATE:** ⊥ draft artifacts until the Characterization Closure Report shows zero unanswered items.

### Step 4: Draft Spec Artifacts

Describe what the code does **today**. ⊥ aspirational. Mark technical debt `[TECH DEBT]`.
1. `specs/DECISION_LOG.md` — discovered decisions, inferred ones marked `[inferred]`.
2. `specs/SPEC.md` — per `../_config/spec-template.md`. Invariants the code enforces → §8. Where the existing system deviates from the Equivalence Profile, record the deviation in §11 (it is the existing behavior; changing it is a later Class 1 decision).
3. `specs/DESIGN.md` (UI only) — tokens extracted from CSS/styles.
4. `specs/contracts/` — `manifest.json` + the matrix-required artifacts, extracted from code: routes → `openapi.yaml`, migrations / live DB → `schema.sql`, error handling → `errors.json`, lifecycle logic → `statecharts.json`. Deviations from the profile → `manifest.json#profileOverrides`.
5. `specs/IMPLEMENTATION_PHASES.md` — all phases `[x]`, with the adoption header:
   > **Note:** Auto-generated by SDD Adoption. All phases pre-checked (existing code). Future changes add new phases via the standard SDD lifecycle.

### Step 5: Record the Characterization Oracle

1. Write `specs/fixtures/oracle.config.json`, and request-only cases (steps without `expect`) in `specs/changes/adoption/requests/` — not in `specs/fixtures/cases/` — for every operation and outcome you identified: success paths, each error, each state transition, illegal transitions.
2. Start the existing system and run `node specs/.sdd/scripts/oracle.cjs record --target default --cases-dir specs/changes/adoption/requests --out specs/changes/adoption/recorded.json`.
3. Review the recorded expectations: replace accidental literals (ids, timestamps the generalizer missed) with matchers; tag recorded bugs `"tags": ["tech-debt"]` — they stay pinned until a Class 1 change fixes them.
4. Move the reviewed `recorded.json` into `specs/fixtures/cases/` (the request-only drafts stay in `specs/changes/`), add `phase: 1` and `derivedFrom: ["recorded:…", "<code file:line>"]`.
5. Map existing tests → invariants. Flag `[UNMAPPED]` tests and `[UNTESTED]` invariants; every `[UNTESTED]` invariant gets an oracle case.

### Step 6: User Review

Present all drafted artifacts and the recorded oracle. The user knows the codebase better → they catch misinterpretations and decide which recorded quirks are bugs.

**⛔ GATE:** ⊥ proceed until user explicitly approves adopted spec artifacts.

## Outputs
- `specs/SPEC.md`, `specs/DECISION_LOG.md`, `specs/DESIGN.md` (UI)
- `specs/contracts/manifest.json` + matrix-required contracts
- `specs/fixtures/oracle.config.json` + characterization cases
- `specs/IMPLEMENTATION_PHASES.md` (pre-checked)
- `specs/backprop-log.md` (created empty if not present)
- `specs/.sdd/_config/sdd-state.json` (via `sdd.cjs transition`)

### Handoff / Transitions
1. **Update state:** `node specs/.sdd/scripts/sdd.cjs transition --completed 01b --project-type <type>`.
2. **Handoff:** Present next-step options:
   - **Option A (Harden Spec, recommended)**: Route `02_adversarial_swarm_analysis` — validate contracts, find gaps the characterization missed.
   - **Option B (Expand Spec)**: Route `01_brainstorming` — the adopted spec is the baseline for new features (Class 1).
   - **Option C (Freeze as-is)**: Route `04_writing_implementation_phases` — the recorded cases replace Stage 02's Outcome Table; run `sdd.cjs check`, then freeze with the user's approval. Required before any Stage 05 work, including refactors (Class 0) that must stay equivalent to the original.
